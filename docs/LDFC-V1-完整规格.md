## 阅读约定：本文只写"用户决策"

本文记录的是**用户已经明确确认的产品决策**。凡是 Agent 为了能跑起来而自己选的

## 1. 项目定义与边界

在 Linux.do 原有 Discourse 信息流之上，增加一个**完全本地化的个人信息流管理层**。

| 谁负责 | 负责什么 |
|---|---|
| Linux.do / Discourse | Topic 内容、排序、阅读位置、未读状态、新回复、第一个未读位置、分页 / Infinite Scroll、SPA 路由 |
| 本扩展 | 个人 Topic 池、主信息流过滤、本地状态、自动补位、Swipe、新回复 UI |

四条不可动摇的原则：

1. **主信息流只处理"还没处理的东西"。**
2. **「感兴趣」= 值得关注后续，但现在不想让它占据主信息流。**
3. **「已读」= 真实阅读过的自动归档，不是手动标记的。**
4. **「新回复」是独立的临时提醒层，不重新污染主信息流，也不改变归属。**

边界：

- 只改"我个人如何看到这些内容"，**不修改 Linux.do 服务端，不删除任何帖子**。
- V1 完全本地：无账号同步、无云数据库、无第三方 API、无 Analytics、无 Telemetry、无广告。
- 不重新实现 Discourse 已经具备的能力。

## 2. 五区模型

用户界面固定为五个区域：

```
🏠 主信息流    ⭐ 感兴趣    💬 新回复    ✓ 已读    × 不感兴趣
```

**关键结构**：真正的归属只有四个池，`💬 新回复` 不是归属，是临时状态。

```
真正归属（basePool）： HOME / INTERESTED / READ / DISMISSED
临时状态（newReplyPending）： 布尔值
```

因此：

> **一个 Topic 永远只有一个主要归属；「新回复」是独立的临时待处理索引，不改变归属。**

示例：

```
Topic A：basePool = INTERESTED，newReplyPending = true
  → 同时出现在「⭐ 感兴趣」和「💬 新回复」
  → 这不是状态冲突，因为一个是归属，一个是提醒

用户读完（Discourse 确认 unread = 0）
  → newReplyPending = false
  → 「💬 新回复」里消失
  → 「⭐ 感兴趣」里一直都在，不受影响
```

**计数规则**：某 Topic 进入新回复区时，「感兴趣 / 已读」的数量**不减**，只有「新回复」+1。

## 3. 各池语义

### 🏠 主信息流

目前尚未被处理的 Topic。属于其他任何池、或有待处理新回复的 Topic 都不显示在这里。

以下行为**不改变状态**：滚过、看到标题、Topic 加载进 DOM、鼠标悬停。

### ⭐ 感兴趣

用户在列表页看到标题、作者、回复数等**外部信息**后判断"值得关注后续，但现在不想看"。

- **不需要先打开 Topic**，看到外部信息即可标记。
- 标记后立即从主信息流消失。

### ✓ 已读

用户**真正打开并阅读过**，由 Discourse 阅读状态确认后**自动形成**。

- 第一版**不提供**手动"已读"按钮。
- 判定细节见第 6 节。
- 「已读」与「感兴趣」不是同一种东西：**自动已读的数量会远大于手动感兴趣**
  （读过的帖子天然比主动关注的帖子多），所以已读区必须按"可能有上万条"来设计。

### 💬 新回复

「感兴趣」或「已读」的 Topic 出现新的未读回复时进入。

- 「不感兴趣」**永远不进入**。
- 数量取**当前** Discourse 未读状态，不做本地历史累计（见第 5 节）。
- 只保留**一个** Topic 条目，多次新回复只更新数字。

### × 不感兴趣

用户明确不希望这个 Topic 再进入自己的信息流。

- 永久有效，**不自动过期**。
- 不因新回复重新出现，不进入新回复区。
- 只能由用户主动恢复。
- V1 只针对**当前 Topic ID**，不做作者 / 分类 / 关键词屏蔽。

## 4. 状态流转

| 起点 | 操作 | 终点 |
|---|---|---|
| HOME | 什么都不做 | HOME |
| HOME | 打开 Topic，Discourse 确认已读 | READ |
| HOME | ⭐ 感兴趣 | INTERESTED |
| HOME | × 不感兴趣 | DISMISSED |
| INTERESTED / READ | 出现未读回复 | 归属不变，newReplyPending = true |
| INTERESTED / READ | 新回复读完 | 归属不变，newReplyPending = false |
| 任意池（含新回复） | × 不感兴趣 | DISMISSED |
| 任意非 HOME 池 | [移回主信息流] | HOME（状态重置，含清掉 newReplyPending） |
| DISMISSED | 出现再多新回复 | 仍然 DISMISSED，不进入新回复 |

**「移回主信息流」是状态重置**：清除当前个人归属，让它重新成为一个待处理的 Topic。
之后再次打开，按新的生命周期走（HOME → READ），不保留旧归属。

## 5. 新回复机制

### 5.1 数据来源

**决策**：新回复、未读数量、第一个未读位置，一律**优先复用 Discourse 原生机制**，
不自己维护第二套"用户看到第几楼"的算法。

阅读位置、未读数量、新回复、第一个未读位置都属于 Discourse 的领域；
插件只负责"这个 Topic 要不要出现在新回复区"。

> 【实现候选】具体读哪些字段（例如列表接口里的 `last_read_post_number` /
> `unread_posts` / `highest_post_number`，或 Topic 详情接口里的楼层流），
> 由 Phase 0 技术侦察后确定。**这不是需求，是可以换的。**

### 5.2 数量不做本地累计

```
10:00  发现 +3        → 显示 +3
11:00  又来 +5        → 显示 +8（当前总未读），不是 +3 / +5 两个条目
```

本地只保存"这个 Topic 有待处理的新回复"，具体数量以当前 Discourse 状态为准。

### 5.3 预览取第一条，不取最新一条

```
上次阅读 #100
#101 张三：……
#102 李四：……
#103 王五：……

卡片预览 → 张三的那条（#101）
```

### 5.4 预览内容

只显示**安全、轻量的纯文本摘要**，不在卡片里渲染 Markdown / 图片 / HTML / 引用 / 代码块。

复杂内容退化为提示：`[包含图片]`、`[包含代码]`、`[包含引用]`。真正要读就点进原 Topic。

### 5.5 卡片内容

```
┌──────────────────────────────────────┐
│ Topic 标题                            │
│ 💬 新回复 5        更新于 10 分钟前    │
│ 张三：“第一条新回复的内容预览……”     │
│ [进入未读位置]                        │
│ [移回主信息流] [× 不感兴趣]           │
└──────────────────────────────────────┘
```

### 5.6 完成判定

**决策**：以 Discourse 原生阅读状态为准，**不自己定义"读完"**。

- 进入新回复时，**跳转到 Discourse 原生的"第一个未读位置"** ——
  也就是复用原站已有的阅读位置机制，而不是插件自己算一个楼层号。
- 用户正常阅读后，原站更新阅读位置。
- 只要原站认为没有未读了，立即从新回复区移除。
- **不要求用户返回列表**：读完直接关闭标签页也算完成，下次插件自然检查时移除。
- 用户中途返回不算完成，继续保留。

> 【实现候选】编辑 `/t/<slug>/<id>/<postNumber>` 这类链接的具体楼层号算法
> （例如 `last_read_post_number + 1`）只是一种实现方式。
> Phase 0 若发现原站有更直接的入口（例如现成的"跳到第一个未读"按钮或路由），
> **应当直接改用原站机制**。

### 5.7 发现方式：被动发现优先

利用用户正常浏览时原站已经产生的数据（页面已加载的列表、`/latest.json`、`/unread.json`）来发现新回复。

**禁止**为了检查历史 Topic 而建立高频后台轮询，也禁止逐个请求本地记录的每个 Topic。

自然检查时机：打开 Linux.do、刷新、切换列表、页面自然更新、从 Topic 返回列表。

## 6. 已读判定

两条**必须同时满足**：

1. **安装之后用户真正打开过**这个 Topic（扩展自己记录的访问）；
2. **Discourse 确认了阅读状态**。

拆开来看，两条各管一件事：

- **"有没有真的进去过"** 由插件判断 —— 这是插件必须自己持有的前提，
  也是"从今天开始记录"能成立的原因；
- **"算不算读完了"** 由 Discourse 判断 —— 插件不定义停留时长、滚动比例这类指标。

> 【实现候选】第 2 条的具体探测方式（例如取列表接口或详情接口里的
> `last_read_post_number` 是否有值），由 Phase 0 确认真实站点实际暴露的字段后定。
> 不同 Topic 类型、登录状态、Discourse 版本下字段可能不同，
> 需求只要求"以 Discourse 的原生已读信号为准"，不指定用哪个字段。

推论：

- 列表里滚过、加载到屏幕、悬停 → **不算已读**。
- 安装前打开过的 Topic，即使原站有阅读记录，也留在主信息流，直到安装后再次打开。
- 用户手动放进「感兴趣」的 Topic，之后打开**不会**被改成已读 —— 尊重用户选择。

### 登录 / 未登录双模式

**决策**：未登录用户也要能用五区，并以本地状态作为兜底。

| | 阅读状态来源 | 新回复判断依据 |
|---|---|---|
| 已登录 | Discourse 的用户级阅读状态 | 原站未读状态 |
| 未登录 | **本地兜底** | 本地记录的已读进度 |

未登录模式的定位：

- 原站不给匿名访客持久的用户级阅读位置，所以这个模式**能力更弱**，但五区都能用。
- **未登录期间产生的本地状态，登录后继续保留**，不清空、不重置；
  登录只是让 Discourse 阅读状态变得可靠，**不覆盖**用户已经整理好的归属。
- **不允许**为了给未登录用户补齐功能而引入云端同步或后台高频扫描。
- Phase 0 **必须专门调查**：Linux.do 对匿名访客到底提供哪些阅读状态字段。
  **不能假设匿名用户和登录用户完全一样。**

> 【实现候选】未登录时"用打开 Topic 那一刻的最高楼层作为本地进度基线、
> 后续楼层增加即视为新回复"这套算法，是 Agent 提出的候选实现，
> **不是用户确认过的产品决策**。它的具体形态要等 Phase 0 查清原站对匿名访客
> 实际提供什么之后再定稿。

## 7. 主信息流与自动补位

用户处理掉的 Topic 平滑消失，下面的自动顶上来。

```
优先使用当前页面已加载的数据
  ↓ 不足时
复用 Linux.do 原有分页 / Infinite Scroll，有限加载
  ↓
本地过滤
  ↓
补位
```

硬性护栏（保护 Linux.do）：

- 当前可显示的主信息流 Topic 足够时**不发任何请求**；
- 一次进入某路由只做**有限**补充，不做无限循环；
- 补充请求之间**必须节流**，达到目标立即停止；
- 用户停止滚动即停。

**禁止**：无限循环请求、后台高频轮询、每秒请求、每个 Topic 单独 API 请求、一次预取大量 Topic。

### 7.1 触发方式：只在用户自然接近底部时补位（已决策）

**决策**：

> 自动补位**只在用户自然接近当前列表底部时触发**。
> **禁止**插件通过 `scrollIntoView`、强制滚动或任何等价手段主动把页面滚到底。

也就是说，正确行为是：

```
用户正常浏览列表中部
        ↓
插件不动（即使主信息流暂时不满）
        ↓
用户自然接近底部
        ↓
触发有限补页 → 过滤 → 补位
```

而不是：

```
用户正在看第 8 条
        ↓
插件发现可见条目不足
        ↓
强制滚动
        ↓
用户突然被甩到页面底部
```

**明确接受的产品后果**：用户没有接近底部时，主信息流**可能暂时没有补满**。
这是刻意的取舍，因为"不打断正常浏览"优先于"列表永远铺满"。

仍然受第 7 节全部护栏约束：不轮询、不预取、有节流、达到目标即停。

> 这条决策取代了此前"用 `scrollIntoView` 把 `.load-more-sentinel` 带进视口"的
> 【实现候选】—— 该候选在真实站点上被证实会把用户正在阅读的页面强制滚到底
> （哨兵位于文档最底部），因此废弃。

> 【实现候选】具体数值（补几页、间隔几秒、可见数量阈值）**由 Agent 先取保守初值
> 用于 MVP 验证**，最终值必须经 Phase 0 技术侦察和真实站点测试后确定。
> 需求只规定"必须限速、必须有限"，**没有指定任何具体数字** ——
> 这些数字不是产品硬性决策，可以调整。

## 8. 导航与 UI 原则

### 8.1 五区导航在 Linux.do 页面内

```
🏠 主信息流 128   ⭐ 感兴趣 31   💬 新回复 ⑦   ✓ 已读 894   × 不感兴趣 73
```

- 「💬 新回复」的数字是**当前待处理的新回复 Topic 数**（动态提醒）；
- 其他数字是各池 Topic 数量；
- 点击即切换信息池，**不需要离开 Linux.do**。
- 导航可以收起成悬浮球（保留新回复徽标）：鼠标移入自动展开、移出收起；
  点过面板内容后保持展开，点面板外部或按 Esc 收起。展开态悬浮球由面板
  连续放大替代（球本身淡出），不再作为第二个收起入口。
- 悬浮球是唯一的位置基准：把球拖到任意位置，面板自动朝屏幕里侧展开
  （球在右半边向左展开、左半边向右展开；下半边向上、上半边向下），
  收起时面板朝球的方向缩回，球本身不会跳到别处。
- 二级面板（信息池 / 设置）沿用同一套展开语义：从导航面板（展开态）或悬浮球
  （收起态）的位置放大出现，收起时朝同一方向缩回；面板因为排序、标记而
  原地重绘时**不重复播放**展开动画。
- 二级面板必须**贴着一级面板**打开（一级在屏幕左半边就在它右侧，反之在左侧；
  上下与一级对齐），不钉在屏幕边缘；窗口窄到放不下时允许盖住一级面板。
- **每个二级面板都必须自带关闭入口**（标题行右侧的 ×）：信息池的四个池子各自
  有，设置面板也有；不允许出现"只有切到设置才有 ×"这种间接出口。
- 关闭二级面板必须走**与展开同一套收缩动画**（朝导航面板 / 悬浮球方向缩回，
  360ms，同样受动画速度倍率影响），不允许"啪"一下消失；收起过程中面板不能
  继续拦截点击。
- **启动形态可切换**：要么是展开的一级面板（默认，与 V1.0 观感一致），要么
  只留一颗悬浮球；用户在设置里选择后立即生效，并在下次打开站点时保持。
- 动画速度必须可调（慢 10 倍 ~ 快 2 倍，1× 为默认），用户看不清动画时
  可以自己放慢；该设置只影响动画，不改变任何交互结果。
- 悬浮球图标固定为**「信息流三行」**（三条横线 + 右侧圆点），与五区入口语义一致。
- 一级面板与二级面板统一**「点开 / 点收」**：再次点击当前已打开的池子
  （或已打开的设置按钮）＝ 收起；点其他池子＝直接切换，不先收起再展开。
  这样同一个入口既能进也能出，不依赖另一个 × 才能关闭。
- 扩展 Popup 只负责设置、数据管理，不作为五区主入口。

### 8.2 原站 UI 为主，插件只做轻量增强

保持 Linux.do 原有 Topic List 的视觉与信息密度，只增加状态与操作信息。
**不**把论坛重做成卡片流 / Tinder 式界面 —— 否则原站一改版就大面积返工。

### 8.3 各池独立滚动 + 分批渲染

五个池使用**统一的 Topic List 展示容器**，但每个池拥有自己的列表与滚动位置，
数据不足时再逐步加载。用户从「主信息流」→「已读」→ 回到「主信息流」，
应该停在原位置，而不是跳回顶部。

**已读区可能积累上千甚至上万条，绝不能一次性全部渲染进 DOM**，
必须分批渲染 / 分页，或使用虚拟列表。具体技术方案由实现根据 UI 框架决定。

各池的数据来源分工：

| 池 | 数据来源 |
|---|---|
| 🏠 主信息流 | 尽量复用 Linux.do 原有的分页 / 无限滚动 |
| ⭐ 感兴趣 / ✓ 已读 / × 不感兴趣 | 主要使用本地数据库分页（这正是要保存最小元数据的原因） |
| 💬 新回复 | 按当前需要动态读取 Discourse 数据 |

### 8.4 时间显示

| 池 | 显示的时间 |
|---|---|
| ⭐ 感兴趣 | 加入感兴趣的时间 |
| ✓ 已读 | 最近阅读时间 |
| 💬 新回复 | 最新新回复时间 |
| × 不感兴趣 | 进入屏蔽区的时间 |

默认相对时间（刚刚 / 10 分钟前 / 昨天 / 3 天前），悬停显示精确时间。

列表页（`/latest`、`/unread` 等 Topic 列表）额外在行尾显示**主题创建时间**
（`MM-DD HH:MM`），按新旧分三档着色：90 天以内正常、30~90 天橙色、更早灰化。
数据只认"确实是创建时间"的来源（行上的 `data-created-at` / `data-topic-created-at`，
或 `td.age[title]` / `td.activity[title]` 里的「创建日期：…」）；
读不到就不显示，**不退而求其次拿"最后活动时间"冒充创建时间**。

### 8.5 主题预览窗口

- 点击主题标题时由插件自己弹预览窗口，不再整页跳转：窗口**同步**插入 DOM
  （按下就有反馈），正文随后由引擎按 `/t/<id>.json` 等站内接口填充。
- 窗口正文使用 vendored 的「LinuxDo 增强阅读」引擎
  （`vendor/linuxdo-enhanced-reading.js`，MIT，作者 Fashion，v1.8.7，随扩展本地分发）：
  楼中楼、点赞、回复、Boost、书签、图片灯箱、楼层滑块直接沿用，
  **不做二次改写**；插件只接管"什么时候弹窗"。
  这是纯本地代码，不引入第三方服务，也不改变"数据只存本地 / 可选 WebDAV"的边界。
- 窗口出现时**从被点击的标题位置放大展开**（FLIP 转场，约 460ms）；
  系统开启"减少动态效果"时直接显示。
- 窗口内提供三个操作入口（⭐ 感兴趣 / ✓ 已读 / × 不感兴趣），标记成功后自动关闭。
  它们放在**主贴正文正下方、评论区标题之上**的独立 dock 里（和参考脚本把按钮挂在
  一楼正文末尾的落点一致），默认只露无底色单色图标，
  悬停时图标旋转并横向展开文字标签；不用池子配色，避免在预览窗里抢正文视觉。
  底部「打开原贴」保留整页跳转入口，Esc 或点遮罩也能关。
- dock 下方还有一排**纯文字工具按钮**（对齐「linux.do 小助手」脚本的能力）：
  - `当前查看全部 ↔ 当前只看楼主`：只显示楼主楼层（引擎的 `.ldp-op` 徽标为准，
    楼主的回帖也算楼主），再点恢复；状态写 `LDFCDB.putMeta("previewOnlyOp")`，
    下次打开沿用。引擎懒加载的新评论会自动套用同一筛选。
  - `展开楼中楼`：依次点掉引擎自己渲染的「展示更多回复」，一次把整棵回复树展开
    （最多 40 层，避免个别异常数据无限点）；没有可展开的楼中楼时给一句提示。
  - `随机跳楼`：在 2 ~ 最高楼之间随机抽一层并跳过去（跳过 1 楼主贴），
    用于抽奖 / 随便看看。已加载的楼层平滑滚动 + 高亮，没加载的按楼层号重开预览。
  - `💾 保存到本地`：把**主贴**导出为离线可读的 HTML，图片内联成 base64。
  - `📸 生成快照`：打开快照面板，**勾选要导出的楼层**（默认只勾 1 楼），
    渲染成一张长图（html2canvas，`vendor/html2canvas.min.js`，MIT，本地分发）。
    预览窗里楼中楼会缩进一级列出（`↳`）；勾父楼时子楼随父楼一起进图，
    父子同时勾选也不会重复出现；也可以只勾某一层楼中楼单独截图。
    生成后先出预览窗：`下载图片`走浏览器下载（IDM / FDM / 迅雷等可接管），
    `另存为…`用 File System Access API 弹出系统保存对话框（Firefox 回退为普通下载）。
    正文里的图片在生成前统一内联成 data URL，取不到的摘掉，
    避免跨域图片把 canvas 标记为 tainted 导致 `toDataURL` 报错。
    面板选项：PNG / JPEG、二维码（`vendor/qrcode.min.js`，MIT，本地分发）、
    水印（默认开，内容为当前登录用户名）、主题（跟随站点 / 浅色 / 深色）。
    选项写 `LDFCDB.putMeta("snapshotSettings")`，下次沿用。
  - 高度保护：内容高于约 14000px 时自动降 scale；再高就直接报错提示少选几层，
    而不是产出一张被裁掉的半截图（几百楼整段截图会超出画布上限）。
- **真实 Topic 页（`/t/…`）** 的首楼正文末尾有同一套工具排：
  `当前查看全部 ↔ 当前只看楼主` + `💾 保存到本地` + `📸 生成快照`。
  只看楼主用 `#post_1[data-user-id]` 与每层 `article[data-user-id]` 比较
  （对齐小助手脚本的判据），认不出楼主就整段不动 —— 宁可不筛，也不把别人的帖子藏起来；
  状态独立存 `topicOnlyOp`，和预览窗的开关互不影响。
- **按楼层跳转**：点击带楼层号的链接（通知、引用、「跳到回复」、搜索结果里的具体楼层，
  形如 `/t/slug/123/45`）时，预览直接定位到第 45 楼，而不是停在"第一条未读"。
  已渲染的楼层平滑滚动并高亮 1.7 秒；目标不在首屏窗口时，引擎走
  `/t/<id>.json?post_number=N` 拉一段以目标为中心的窗口再定位。
  站外链接、无楼层号的普通 Topic 链接行为不变。
- 打开速度：鼠标划过标题（约 90ms 意图延迟）或按下左键时，把
  `/n/-/<id>.json` 首屏树预取进引擎的 60 秒缓存，点开时命中缓存、少一次往返。
  预取只在预览开关打开、非搜索页、非站外链接时触发，同一 Topic 每次加载只预取一次；
  触摸设备不做悬停预取（等 `pointerdown` 才取）。
- 设置里可关闭（默认开启）。关闭后点击标题回到原站行为，
  由原站或第三方预览脚本接管。
- 第三方预览脚本同时启用时，插件会先关掉对方已经弹出的窗口再开自己的，
  不会叠出两层弹窗。

## 9. 交互

### 9.1 桌面端

默认不显示按钮，保持原页面干净。鼠标悬停 Topic 行时，在行尾出现一枚
中性半透明的图标胶囊（⭐ / ✓ / ×）；鼠标移到某个图标上时，图标旋转一圈并把文字
横向展开（感兴趣 / 已读 / 不感兴趣），移开收回。

```
[ ⭐  ✓  × ]     ← 默认：只有图标
[ ⭐ 感兴趣 ][ ✓ ][ × ]  ← 悬停「感兴趣」
```

同一套图标语言用在三处：列表行悬停、Topic 页首楼按钮行、预览窗主贴下方 dock。
颜色一律跟随页面文字颜色 + 中性半透明底，不按池子配色 —— 亮色/暗色主题都不用另写一套。

主信息流**不提供**「✓ 已读」按钮。

### 9.2 移动端 Swipe

```
右滑 → ⭐ 感兴趣
左滑 → × 不感兴趣
```

- 必须处理 `touchstart / touchmove / touchend`；
- 用 `abs(deltaX) > abs(deltaY) * 阈值` 判定为横向手势，
  **不能**用 `touch-action: none` 粗暴禁掉页面滚动。

### 9.3 点击后的动画

```
轻微状态反馈 → 150～400ms 平滑收起 → 释放空间 → 下一条顶上
```

最终必须**真正释放页面空间**，不能只变色然后一直留在那里。

### 9.4 各区操作按钮

| 区域 | 按钮 |
|---|---|
| 主信息流 | `[⭐ 感兴趣]` `[× 不感兴趣]` |
| 感兴趣 | `[移回主信息流]` `[× 不感兴趣]` |
| 已读 | `[移回主信息流]` `[× 不感兴趣]` |
| 不感兴趣 | `[移回主信息流]` |
| 新回复 | `[进入未读位置]` `[移回主信息流]` `[× 不感兴趣]` |

不设计大量互相重复的按钮。

**「移入…」（V1.1 起）**：信息池面板里每条记录额外提供 `[移入…]`，
展开后列出**除当前池以外**的其他池子，点一下直接改归属，不必先移回主信息流。
目标受池语义约束：`新回复` 只接受「感兴趣 / 已读」来源，其他来源的目标按钮
显示为禁用并说明原因，不做静默改写。

> **关于「不感兴趣」区**：用户的要求是"除主信息流外，其他区提供 `[移回主信息流]`
> 以及不感兴趣"。V1 **当前采用**的做法是该区只显示 `[移回主信息流]` ——
> 因为在一个已经屏蔽的区里再放一个"× 不感兴趣"没有意义。
> 这是**实现层的一次取舍，不是用户明确拍板的规则**；如果用户要求严格按字面来，
> 该区补上 `[× 不感兴趣]` 即可，不影响任何状态逻辑。

### 9.5 Undo 与长期恢复（两层）

- 点「× 不感兴趣」后立即隐藏，并弹出 Toast：`已移入"不感兴趣" [撤销]`，保留 3～5 秒。
- Toast 消失后，「不感兴趣」区仍然可以 `[移回主信息流]`。
- 即时撤销 + 长期恢复，两种机制都在。

### 9.6 改池只走显式操作

不提供"在列表里自由拖拽 Topic 排序 / 随手改池"的交互。四个池的语义是明确的
（感兴趣 = 主动关注 / 已读 = 实际读过 / 不感兴趣 = 明确屏蔽 / 新回复 = 暂态工作区），
允许任意拖拽会把这些语义重新混在一起。

V1 只通过明确操作改变归属：`[移回主信息流]`、`[× 不感兴趣]`，
以及自然发生的"打开并被 Discourse 标记为已读""出现新回复"。

V1.1 起可用的**显式**改池方式：

- 信息池里的单条 `[移入…]`；
- 长按多选后的批量移入（9.7）；
- 按住行上的 `[⭐ ✓ ×]` 按钮组拖动后的**拖拽投放**（9.8）。

> 拖拽投放不是"自由拖拽"：它只是一次移入操作的输入方式。
> 目标规则、跳过规则与 `[移入…]` 完全一致，不会因为"拖了"就获得额外语义。

### 9.7 长按多选（批量选中）

```text
长按任意一行的 [⭐ ✓ ×] 按钮组（500ms）
        ↓ 按钮组抖动
进入多选 → 点各行按钮组 = 勾选 / 取消勾选
        ↓ 按住任意一枚并拖动
拖拽投放（9.8）→ 落到目标池子格 = 批量移入
```

- 入口就是**已经存在的行操作按钮组**，不新增"多选"按钮、不多一层 UI。
- 多选期间：点按钮组的**任意位置**＝勾选 / 取消勾选整条，**不执行原来的标记动作**；
  导航显示「已选 N」。
- **点标题永远照常浏览 / 开预览**，多选不拦截标题点击。
- 再点一次同一个已选中的按钮组 = 只取消这一条，**不退出**多选。
- 快速连续点击同一个按钮组同一位置两次 = 退出多选。
- 退出方式：`Esc`、点悬浮球、点页面空白，以及 Toast 上的「退出」和上面的双击退出。
- 目标规则与单条 `[移入…]` 完全一致：`新回复` 只接受「感兴趣 / 已读」，
  其余跳过并在提示里说明跳过了几条。
- 多选态点导航里的池子**只给提示、不批量移入**：移入统一走拖拽投放，
  避免"点一下就把选中的东西全搬走"这类误操作。
- 长按不能吞掉正常点击：普通点击仍然执行标记；长按松手时浏览器补发的那次
  `click` 必须被忽略（否则会立刻误选一行）。
- 触屏长按不得弹出系统菜单（拦截 `contextmenu`），否则入口会被系统菜单挡住。
- 覆盖范围：主信息流、搜索结果页、话题页底部的推荐 / 相关列表。
  搜索页仍然**不做五区过滤（当前池是哪个都一样）、不接管链接点击**，
  只是多了手动标记入口与已加入光效。

### 9.8 拖拽投放（drag-to-pool）

```text
按住 [⭐ ✓ ×] 按钮组并移动（> 6px 即进入拖拽）
        ↓
按钮组跟手移动；周围展开五个池子格（半圆扇形）
        ↓
把按钮组移到某一格上 → 该格高亮
        ↓ 松手
移入该池（多选态 = 批量移入选中的全部），按钮组弹回原位
```

- **不新增任何按钮**：拖拽的起点就是行上已有的按钮组。
- 拖拽的是"这枚按钮组所属的那条 Topic"。列表页只有鼠标所在行会显示按钮组，
  帖子页则对应当前主帖，不会串到别的行上。
- 多选态下按住并拖动 = 投放**已选中的全部**；未多选时 = 投放这一条。
- 面板以**按下那一刻的按钮组中心**为圆心展开，不跟着指针跑
  （否则指针永远在圆心，外圈格子永远够不到）。命中判定用按钮组中心。
- 顶部空间不足时整圈翻到下方，格子不会跑出视口。
- 不可用的目标格（例如未归入感兴趣 / 已读时的「新回复」）置灰但保留，
  避免用户以为少了一格。
- 松手后按钮组带回弹动画复位，面板立即收起。

### 9.9 池子光效（已加入状态）

- 首楼三按钮、列表行按钮组、预览窗 dock：只要该 Topic 的 `basePool` 命中某个池子，
  对应按钮就带**底部渐变指示条 + 光晕**，颜色：

  | 池子 | 颜色 |
  |---|---|
  | ⭐ 感兴趣 | `#ffb454` |
  | ✓ 已读 | `#5fd0a8` |
  | × 不感兴趣 | `#e0777d` |

- 信息池面板里的条目**不做**光效（面板本身已按池子分区，再加一层是噪音）。
- 判定只看 `basePool`：`newReplyPending` 之类的临时标记不影响光效。
- 任何改池路径（按钮、移入、拖拽投放、自动已读、同步合并）都必须点亮 / 熄灭光效，
  统一由 `ldfc:pool-change` 事件驱动。

## 11. 数据与隐私

### 11.1 本地数据库

用 **IndexedDB**（不用 localStorage 作主数据库）。

本地保存：

```
topicId            唯一标识
basePool           真实归属：HOME / INTERESTED / READ / DISMISSED
newReplyPending    临时状态
enteredPoolAt      进入当前池的时间
createdAt / updatedAt
展示元数据          title / slug / excerpt / category / 最后回复人 / 最后活动时间
未登录兜底进度       readUpToPostNumber（仅未登录模式使用，见第 6 节）
预览缓存            previewAuthor / previewText / previewForRead（缓存，不是事实来源）
```

**不保存帖子正文。**

### 11.2 唯一标识

全系统只认 **Topic ID**。不依赖标题、作者、时间、回复数、列表位置、第几页。
所以 `/latest`、`/top`、分类页里的同一个 Topic 一定是同一个。

### 11.3 多账号隔离

同一浏览器可能有多个 Linux.do 账号。**每个账号使用完全独立的本地状态空间**，
未登录用户也有独立的 guest 空间：

```
guest/        Topic A → 感兴趣
user-<id-A>/  Topic A → 已读
user-<id-B>/  Topic A → 主信息流
```

- 不得互相污染。
- 用户标识必须用**稳定 ID**，不能想当然拿用户名当永久 ID —— 用户名可以改，改完状态就"丢了"。
- 未登录期间的本地状态，登录后**继续保留**，不清空、不重置；
  登录只是让 Discourse 阅读状态更可靠，**不覆盖**用户已经整理好的本地归属。

> 【实现候选】身份来源与 ID 形式（当前用 `/session/current.json` 返回的数值 user id，
> 降级用页面头部的用户名）。具体以 Phase 0 在真实站点上的调查为准。

### 11.4 导入导出

- 导出 JSON 只包含：Topic ID、池状态、时间戳。
- **不包含**：帖子正文、Cookie、密码、Token、账号凭据。
- 导入前必须逐条校验格式，错误 JSON 不能破坏现有数据。

### 11.5 数据清理

V1 **只提供手动清理**，不自动清理（避免"处理过的帖子几年后突然又跑出来"）。

```
[清理感兴趣]  [清理已读]  [清理不感兴趣]  [清理全部]
```

- 必须二次确认，并显示条数；
- 明确告知：清理的是扩展自己的本地数据库，**不会删除 Linux.do 上的任何帖子**；
- 清理后这些 Topic 重新被视为「主信息流」的未处理内容。

### 11.6 性能要求

插件必须轻量。启动时一次性把本地状态载入内存（`Set` / `Map`），
之后过滤 DOM 直接查内存：

```
启动 → IndexedDB 一次性读取 → 放进内存 Map
过滤 DOM 时 → set.has(topicId)
```

**禁止**每过滤一个 Topic 就重新查询一次 IndexedDB。

```
A｜从今天开始记录（默认）
B｜根据 Linux.do / Discourse 当前阅读状态初始化
C｜全部视为未处理
```

- B 读取原站已有的已读 / 未读状态一次性建立初始池（需要登录）。
- C 什么都不标记，全部留在主信息流。

## 13. 原站兼容与动态页面

### 13.1 必须支持 SPA

不能只依赖 `window.onload`。需要处理 `pushState` / `replaceState` / `popstate`，
并用 `MutationObserver` 处理新插入的 Topic。

> ⚠️ 实现要点：内容脚本运行在隔离世界（isolated world），
> 在那里改写 `history.pushState` **拦不到主世界（Discourse）的调用**。
> 路由拦截必须注入到主世界（MAIN world）。

### 13.2 MutationObserver 防循环

必须用 debounce + processed marker + 最小范围监听，
禁止产生 `DOM 修改 → Observer → 再次修改 → Observer` 的死循环。

### 13.3 不能破坏原站功能

至少保证：Topic 点击、作者点击、分类点击、搜索、分页、刷新、前进 / 后退、
新标签页、Ctrl+Click、鼠标中键，全部照常工作。

**新标签页打开不算已读。** 用户 Ctrl+Click / 中键打开 Topic 时，原列表页并没有发生
"进入 → 返回"，所以不因这个"打开动作"本身改变主信息流。等用户在那边真正阅读、
Discourse 确认阅读位置之后，再在扩展下一次自然检查时把它归入「已读」。

这条是「阅读状态以 Discourse 为准，而不是根据浏览器点击行为猜测」的直接推论。

### 13.4 作用范围

- 所有普通 Topic List（`/latest`、`/top`、分类页等）**共用同一套本地池状态**。
- 插件**只在用户当前正在看的 Linux.do Topic List 上做过滤**，不另造一个"超级信息流"，
  也不自己实现 Latest / Top / 分类的排序或筛选算法。
  Linux.do 决定"哪些 Topic 出现在这个页面"，插件决定"这些 Topic 中哪些还应该让你看到"。
- 「不感兴趣」是**全局按 Topic ID 生效**的：`/latest`、`/top`、分类页都隐藏。
  因为它的语义是"我不想看到这个 Topic"，而不是"我不想在某个页面看到它"。
- **搜索结果页例外**：用户主动检索时**任何情况下**都不执行五区过滤 ——
  包括用户在搜索页里点过某个池子标签之后。池子归属只用来点亮光效，
  绝不隐藏搜索结果。这让扩展始终是"信息流管理器"，而不是"全站内容屏蔽器"。

## 19. V1.1 云同步（WebDAV / Google Drive）

> **V1.0 仍然是纯本地版本。** 本节是 V1.1 的新增能力：
> 不配置远端时，行为与 V1.0 完全一致，不产生任何外部请求。
> 第 11 节的数据边界、第 2 节的五区模型、第 5 节的新回复机制均不变。

### 19.1 范围与阶段

| 代号 | 方案 | 状态 |
|---|---|---|
| S0 | 手动 JSON 导出 / 导入 | V1.0 已有，V1.1 保持兼容 |
| S1 | WebDAV（坚果云等） | V1.1 本轮实现 |
| S3 | Google Drive（AppData 空间） | V1.1 计划中，排在 S1 之后 |

用户明确接受 S0 + S1 + S3 三种方案；网络连通性由用户自行解决。

### 19.2 同步单元与文件命名

- **一个账号命名空间对应一个远程文件**，绝不把多个 namespace 混在一个文件里。
- 文件名固定为 `ldfc-<namespace>.json`（例如 `ldfc-user-42.json`、`ldfc-guest.json`）。
- 设置里填**目录地址**即可，扩展按上述规则拼文件名；直接填 `.json` 完整地址时原样使用。
- **手填文件名（可选）**：设置面板新增「同步文件名」输入框，留空即按上面规则自动命名。
  用途是脚本版与扩展版识别出的命名空间不一致时（一边拿到 `user-42`，
  一边降级成 `user-<用户名>`）仍能指向同一个文件。手填值会被清洗
  （去掉路径分隔符与控制字符）并自动补 `.json`。
  注意：文件名一致**不等于**可以跨账号合并 —— 远端文件里的 `namespace`
  仍会被校验，不匹配就整体拒绝，这是多账号隔离的底线。

### 19.2.1 远程文件格式（schema 5）

记录上千条时，**字段名比数据本身还占地方**：`"lastPosterUsername":` 这种键
在每条记录里都要重复一遍。所以远程文档分两层处理：先做紧凑编码（schema 2，
仍是可读 JSON），再整体 gzip + base64 封装（schema 3）。本地存储格式完全不变。

**第一层：紧凑编码（schema 2）**

| 措施 | 说明 |
|---|---|
| 短键 | `topicId→i`、`basePool→p`、`title→t`、`slug→s`、`updatedAt→ua`、`lastPosterUsername→u` … |
| 设备字典 | 顶层 `devices: [...]` 只存一份，记录里写下标 `d`（下标 0 直接省略） |
| 省略默认值 | `inNewReply:false`、`unreadPosts:0`、`enteredPoolAt === updatedAt`、`createdAt === updatedAt` 不写，读取时原样补回 |
| 空值不写 | `null` / `""`（`categoryId`、`lastPosterUsername`、`readUpToPostNumber` 等）一律省略 |
| 池名单字母 | `basePool` 写 `h` / `s` / `r` / `x`（HOME / INTERESTED / READ / DISMISSED） |
| 占位不写 | `slug === "topic"` 不写（站点会把 `/t/topic/<id>` 重定向，这个占位没有信息量） |
| 墓碑数组化 | `[["123", 1760000000000], ...]`，不再逐条写键名 |

**第二层：紧凑行 + 整体压缩（schema 4；schema 5 在其上追加两列）**

在 schema 2 之上再做两件事，然后**直接落盘 gzip 字节**：

| 措施 | 说明 |
|---|---|
| 行变数组 | 记录写成定长数组，列序由文档里的 `cols` 声明；大量重复的短键名不再逐条出现 |
| 数字压成 base36 | 毫秒时间戳写成 `"~" + n.toString(36)`；前缀 `~` 用来和普通字符串区分 |
| 裸二进制 | 文件就是 gzip 字节本身，不做 base64 —— base64 会白多占 33% |
| 通知接管标记（schema 5） | 行末追加 `nm`（`notifyManualLevel`）与 `nma`（`notifyManualAt`，走 base36）。未接管过的记录两列都为空，几乎不增加体积 |

读端靠 gzip 魔数（`1f 8b`）区分二进制文件与历史 JSON 文件。

实测（真实数据 294 条记录、0 墓碑）：

| 阶段 | 大小 |
|---|---|
| 未优化（长键 + 全字段） | 58.5 KB |
| schema 2（紧凑编码） | 42.7 KB |
| schema 3（gzip + base64 信封） | 23.6 KB |
| **schema 4（紧凑行 + 裸 gzip）** | **17.3 KB** |
| schema 5（schema 4 + `nm` / `nma` 两列） | 未重新实测；未接管记录两列为空，gzip 后增量可忽略（【推断】） |

**代价（已确认接受）**：远程文件既不是可读 JSON，也不是可解压的文本信封，
坚果云网页预览里会显示为二进制文件；手工导出/导入仍走本地格式，不受影响。

> **`lastPostedAt` 是混合类型**：真实数据里它有时是毫秒数、有时是 ISO 字符串。
> 只有确认是有限数字才转 base36，否则按原字符串保存 —— 否则
> `parseInt("2026-10-31T…", 36)` 会把字符串静默解析成一个随机数字。
> **`d`（deviceId 下标）必须留在列里**：漏掉它会让所有记录的 deviceId
> 退回 `devices[0]`，同 `updatedAt` 的 tie-break 与归属都会算错。

> **读兼容**：`schema: 1` / `schema: 2` 的老远端文件、`schema: 3` 的 base64 信封、
> `schema: 4` 的紧凑文件都能读，不需要手动迁移或删文件；写回时统一升级到 schema 5。
> **跨设备**：schema 5 是单向升级 —— 还没更新的旧版扩展读到新文件会明确报
> 「schema 不兼容」并**中止本次同步**（不会写坏远端数据）。所以升级时要把所有
> 设备上的扩展都更新，再让它们同步。
> **降级**：运行时不支持 `CompressionStream` 时写入明文 JSON（schema 4 文本形式）——
> 文件大一些，但同步功能不会因此失效。

### 19.3 冲突处理

- **逐条合并**，按 `updatedAt` 做后写覆盖（LWW）。**严禁整库覆盖**。
- 同一毫秒的平局用 `deviceId` 字典序 tie-break，保证两台设备算出的结果**完全相同**（收敛）。
  记录若无 `deviceId`，退化为对规范化 JSON 做比较，仍保持确定性。
- 删除用**墓碑**表达（`deletedAt`），不是"远端没有就等于删除"。
- 墓碑保留 90 天后回收，不再上传。
- 预览与阅读基线（`previewForRead` / `readUpToPostNumber`）属于**缓存/兜底**，
  合并时不得因 `updatedAt` 丢失，也不得因此把记录顶到池子最前。
- 通知「手动接管」标记（`notifyManualLevel` / `notifyManualAt`）同样**不参与池子 LWW**，
  用独立的 `notifyManualAt` 比较，谁的时间戳更新听谁的（第 20.4 节）。

### 19.4 自动同步与开关

- 打开站点时 **pull 一次**（同一会话只拉一次）。
- 用户标记后 **debounce 10 秒自动 push**。
- 设置里必须提供**「开启 / 关闭自动同步」开关，默认开启**。
- 关闭后：打开站点不拉取、标记不排推送；手动「立即同步」仍可用。
- 不得引入后台轮询，也不得逐 Topic 发请求（第 5.7 / AC-030 的约束继续有效）。

### 19.5 凭据与隐私

- 凭据（WebDAV 地址 / 账号 / 应用密码）**只保存在本地 IndexedDB**，不上传到任何第三方。
- UI 必须明确提示"凭据明文保存在本地，请勿在公用电脑使用"。
- 必须提供**「清除本地凭据」**按钮；清除需要二次确认，且**不删除远端同步文件**。
- 必须提供**可展开的内置绑定说明**（默认收起），至少覆盖：注册坚果云、
  建同步目录、正确的 WebDAV 地址写法（`dav.jianguoyun.com`，不是
  `www.jianguoyun.com/#/…` 网页链接）、账号填登录邮箱、
  应用密码≠登录密码（在客户端「账户设置 → 安全选项」生成）。
- 同步内容仍然**不含帖子正文**；只同步归属、标题、时间戳、预览缓存等字段（第 11.4 的边界不变）。

### 19.6 跨域与权限

- MV3 下跨域请求只能由 **background service worker** 代发，content script 直连会被 CORS 拦截。
- WebDAV 域名走**可选取权限**（`optional_host_permissions`），在用户点击后于**独立扩展页**申请；
  content script 无法直接调用 `chrome.permissions`。
- 权限按**域名**申请，匹配模式中**不包含端口**。

### 19.7 兼容降级

- 油猴脚本产物复用同一份源码，跨域改由 `GM_xmlhttpRequest` 发送
  （脚本声明 `@grant GM_xmlhttpRequest` + `@connect *`）。
  传输层对外契约完全一致：`read() / write(bytes, etag) / test()`，
  错误必须映射成与扩展后台相同的 `reason`（`auth` / `conflict` / `network` / `http`）。
- 两种后端的判定顺序：**有扩展后台走扩展**，否则看是否有 GM 接口，
  两者都没有时才降级。降级时设置面板只显示说明，不渲染无法生效的表单。
- 本地数据管理与手动 JSON 导出 / 导入在两种环境下都必须可用。

## 20. V1.1 通知级别联动

### 20.1 定位

这里改的是**站点侧状态**（Discourse 的 `TopicUser.notification_level`），
会真实改变你在 linux.do 的邮件 / 推送设置。它不是插件自己的归属数据，
但可以和「移入某个信息池」这个动作联动。

### 20.2 联动规则

- 总开关「与信息池联动」默认开启；关闭后只显示当前档位，不自动写。
- 默认映射：感兴趣 → 关注（3）、已读 → 跟踪（2）、不感兴趣 → 免打扰（0）。
  三档都可在设置里改。
- **只对用户主动移池生效**。自动补位、自动进入已读等系统动作默认不联动。
- 设置里新增**「自动已读时」**：默认「不修改」（`autoReadLevel: null`）。
  用户可单独选择免打扰 / 常规 / 跟踪 / 关注；开启后每篇自动进入已读的帖子
  会发一次通知设置请求，并同样受手动优先与未登录拦截约束。
- 撤销「移入」时**回滚本次操作带来的全部改动**，包括通知级别；
  不额外保留「不覆盖手动值」的特例。

### 20.3 手动优先

- 用户在某条帖子上手动改过档位 → 记为**手动接管**（`notifyManualLevel` + `notifyManualAt`）。
- 接管期间，池子联动与自动已读都**不覆盖**这条帖子。
- 出口是菜单底部「跟随信息池」：清除接管标记，并按当前归属立刻应用一次映射。

### 20.4 接管标记的同步

- 只有「被接管过」这个标记进云同步，当前档位缓存仍只存本地。
- 标记用独立时间戳合并，不修改 `updatedAt`，因此**不会把记录顶到池子最前**。
- `notifyManualLevel = null` 且 `notifyManualAt` 有值，表示用户显式点了
  「跟随信息池」；这个"清除"也要同步，否则另一台设备会把旧标记带回来。
- 老记录只有档位、没有时间戳时按 `at = 0` 处理，任何真实时间戳都能赢过它。
- 远程文件因此升到 **schema 5**（追加 `nm` / `nma` 两列），跨设备约束见 19.2.1。
