## 8. 请求行为观察

| 场景 | 扩展独有请求 | 逐 Topic 请求 | 轮询 | 结论 |
|---|---|---|---|---|
| 登录态静置 40s | **0** | 0 | 无 | 正常 |
| 登录态路由切换 ×5 | `/session/current.json` ×5（整页加载各 1 次） | **0** | 无 | 正常 |
| Guest 静置 40s | **0** | 0 | 无 | 正常 |
| Guest 路由切换 ×3 | `/unread.json` ×3（均 403） | **0** | 无 | **有一次无用请求** |

**关键结论：**

1. **没有任何轮询**。扩展的同步完全由路由变化驱动（`pushState` / `popstate`），与 P0 修复后的设计一致。
2. **没有逐 Topic 请求**。在所有场景下 `/t/<id>.json` 的调用数都是 0
   （因为本轮没有产生"新回复待处理"的记录，所以定向确认一次都没触发 —— 这正说明
   **定向确认是按需的，不是扫全量**）。
3. **tracking 数据优先使用**：登录态下 `topicTrackingStates` 窗口读到 **207 行**，
   扩展零请求即获得未读状态，符合 P0-1 设计。
4. 唯一的多余请求是 Guest 模式下的 `/unread.json`（见第 10 节）。

## 10. 发现的问题

### P2-A：Guest 模式下每次同步仍请求必然 403 的 `/unread.json`

| 项 | 内容 |
|---|---|
| 现象 | 未登录时，每次路由变化的同步都会请求一次 `/unread.json`，返回 **403** |
| 复现步骤 | 全新 profile 打开 linux.do → 在 `/latest` `/top` `/latest` 之间切换 3 次 → 观察请求 |
| 实测证据 | `{总请求: 1203, unread接口调用: ["/unread.json","/unread.json","/unread.json"], 逐Topic请求: []}` |
| 分类 | **实现候选问题**（不是产品问题，也不是测试环境问题） |
| 影响 | 每次同步多 1 个必然失败的请求。不属于 AC-030 的"高频轮询"或"逐 Topic 请求"，但属于**不必要请求** |
| 期望 | 扩展已知自己处于 guest（`identity().loggedIn === false`），可以在客户端直接跳过 `/unread.json` |
| 建议 | 记为待办，**本轮不修**（按本轮"只测不改"的要求） |

### 观察-B：`/session/current.json` 每次整页加载请求一次

| 项 | 内容 |
|---|---|
| 现象 | 每次**整页加载**请求一次身份接口；SPA 内部导航不重复 |
| 分类 | **设计行为，不是缺陷** |
| 说明 | 账号身份解析需要它。Phase 0 已确认 `#data-preloaded` 里也有 `currentUser`，<br>理论上可省掉这次请求 —— 记为**优化候选**，优先级低于 P2-A |

### 观察-C：首次用新 profile 启动可能遇到 Cloudflare 挑战页

| 项 | 内容 |
|---|---|
| 现象 | 无头模式首次启动时返回 `Just a moment...`；改可见窗口重启后直接通过 |
| 分类 | **环境问题**，非扩展问题 |
| 处理 | 未做任何规避（没有反复刷新 / 改 UA / 改指纹），只按既定流程重启一次 |
| 建议 | 已记录；真实站点首次验证建议用可见窗口 |

**本轮没有发现 P0 / P1 级问题。** 因此未按"发现问题就停止扩大测试范围"的规则中断 —— 上述均为 P2 与观察项。
