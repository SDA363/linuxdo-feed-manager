## 13. 本次覆盖的行为

【已验证】

- 真实未读状态能被**发现**为 `newReplyPending`
- 「新回复」是**临时层**：`basePool` 全程保持 `INTERESTED`，原池计数**不减**
- 同一 Topic 可**同时**属于「感兴趣」并出现在「新回复」
- 新回复**数量**取自原站未读状态（3 = 60−57）
- **最新回复时间**正确显示（绝对时间 + 相对时间自洽）
- **第一条未读回复预览**取第 58 楼，**不是**最新一条
- 「进入未读位置」跳到 **第 58 楼**（57+1），与原站第一个未读一致
- 读完后 `unread = 0`（`/unread.json` 不再包含该 Topic，`last_read = highest = 60`）
- `NEW_REPLY` **立即消失**，`basePool` **不变**
- 处理新回复**不会**减少原池计数
- 标记动作走的是**真实 UI**（悬停后点击行内按钮），不是内部 API

## 14. 本次没有覆盖的实时性问题

【尚未验证】

> **Topic 在用户正常浏览期间"刚刚产生新回复"的实时发现时效性。**

原因：本次使用的是**已经存在的**未读状态（`last_read=57 / highest=60`），
而不是"扩展运行期间服务器新到了一条回复"。要验证后者需要：

- 第二个账号给该帖回复，或
- 等待陌生人回复

当前用户**没有第二个 Linux.do 账号**，因此这一项暂时无法验证。

**不能把本次结果表述为"实时新回复检测已验证"。** 准确的表述是：

```
NEW_REPLY 行为闭环            ✅ 已验证
已有未读状态的发现             ✅ 已验证
第一条未读定位                 ✅ 已验证
原池归属保持（Q58）            ✅ 已验证
完成后清除 pending             ✅ 已验证
                              ─────────────
实时新回复的发现时效性          ⏳ NOT TESTED
```

### 附带发现（观察项，非缺陷）

读完后记录里的 `unreadPosts` 仍为 `3`、`lastReadPostNumber` 仍为 `57`（未随清除而更新）。

- **影响**：无用户可见影响 —— 该 Topic 已不在「新回复」区，不会再渲染数量与预览。
- **为何会自动纠正**：下一次发现新回复时，`discoverNewReplies` 会用 tracking 里的
  `lastReadPostNumber`（届时为 60）覆盖记录，预览目标楼也会随之变成 61。
- **结论**：属于**短暂过期元数据**，会自愈。记为观察项，**不作为缺陷**，本轮不改代码。
