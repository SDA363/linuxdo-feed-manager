## 1. 修改前行为

【事实】改动前 `core/autofill.js` 的触发方式：

```js
more.scrollIntoView({ block: "end", behavior: "smooth" });
```

即：把 `.load-more-sentinel` 平滑滚动进视口，以此驱动 Discourse 的原生无限滚动。

【真实站点实测】哨兵的位置（改动前采集）：

| 指标 | 值 |
|---|---|
| 哨兵 `top` | **2586** |
| 视口高度 | 752 |
| 文档高度 | 2687 |
| **哨兵距当前视图底部** | **1935 px** |

→ 一旦触发，用户正在阅读的页面会被强制平滑滚动约 **1935px**。

**这违反了产品的两条既有原则**：不打断正常浏览、模拟真实用户行为。

---

## 2. 修改内容

**唯一改动文件：`core/autofill.js`**（约 10 行实质改动）

| # | 改动 | 说明 |
|---|---|---|
| 1 | **删除** `more.scrollIntoView({block:"end"})` | 打断阅读的根源 |
| 2 | 新增 `sentinelInViewport()`，并纳入 `shouldLoadMore()` 门控 | 哨兵必须已进入视口（含下方 120px 余量）才允许补位 —— 这就是"用户已自然接近底部"的判据 |
| 3 | 触发方式改为**派发一次 `scroll` 事件** | 驱动 Discourse 原生无限滚动，**不改变任何滚动位置** |
| 4 | 新增 `dispatchPending` + 600ms 冷却 | 防止 DOM 更新 → observer → 再次派发的循环 |

**新增的完整门控链**（全部满足才补位）：

```
激活池 = HOME
  AND 本次路由触发次数 < 2
  AND 距上次触发 ≥ 3000ms
  AND 可见主信息流行数 < 8
  AND 哨兵已在视口内（新增）
```

**护栏全部保留**：不轮询、不逐 Topic 请求、不大量预取、达到目标即停。

新增三个只读辅助导出（供测试断言用，不改变行为）：
`sentinelInViewport` / `shouldLoadMore` / `visibleHomeRowCount`。

### 为什么"哨兵在视口内"就等价于"用户接近底部"

| 场景 | 哨兵位置 | 是否补位 | 是否打断用户 |
|---|---|---|---|
| 用户在长列表中部 | 视口外很远（实测 1935px） | **不补位** | 否 |
| 用户自己滚到底 | 进入视口 | 补位（原站自己也会加载） | 否 |
| 过滤后内容太短、没得滚 | 本来就在视口内 | 补位 | 否（没有内容可滚，不存在打断） |

## 3. 本地测试结果

**49 项通过 / 0 项失败**（44 项原有 + 5 项新增）

新增 5 项：

```
PASS：哨兵不在视口时不补位也不滚动（maybeFill=false，scrollY 0→0，行数 31→31，分页请求 0）
PASS：用户滚动后扩展不改变滚动位置（scrollY 1540→1540；门控 sentinelInView=true,
      visibleHomeRows=32, shouldLoadMore=false；maybeFill=false）
PASS：自动补位源码不含任何滚动调用（无 scrollIntoView / scrollTo / scrollBy / scrollTop=）
PASS：不会无限重复补位（加载后 sentinelInViewport=true，再次 maybeFill=false，新增请求 0）
PASS：过滤后列表变短时可在原地补位（可见行 6，sentinelInViewport=true，maybeFill=true，scrollY 0→0）
```

**原有 44 项全部保持 PASS** —— AC-030 / AC-031 / AC-034 / Guest 均未受影响。

### 为做本地验证而补充的 fixture 能力

原 fixture 没有 `.load-more-sentinel`，自动补位在本地**完全测不到**。因此补齐：

- 列表页底部新增 `<div class="load-more-sentinel">`
- 新增 60 条 Topic，让 `/latest.json` 有第 1、2 页可翻
- `/latest.json?page=N` 支持真实分页 + `more_topics_url`
- 页面内新增一段**模拟 Discourse 原生无限滚动**的脚本：监听 `scroll`，哨兵进视口就加载下一页并追加行

> 这段模拟脚本是必要的 —— 扩展的新方案是"派发 scroll 事件驱动原站"，
> 如果 fixture 没有对应机制，就无法验证"派发确实能驱动加载"。

### 测试过程中修正的两处自身错误（如实记录）

1. **B 项最初写错了预期**：我原以为"滚到底后 maybeFill 应返回 true"，
   实际是用户滚到底 → 原站自己加载下一页（31→61 行）→ 哨兵被推离视口 →
   扩展此时**不补位才是正确的**。已改为断言真正的产品要求：**滚动位置不被改变**。
2. **源码检查正则误判**：`/scrollIntoView/` 匹配到了注释里的
   "不调用 scrollIntoView" 字样。已改为**先剔除注释再检查**。

### B. 用户自然往下滚动的全过程

| 项 | 内容 |
|---|---|
| 操作步骤 | 5 次「向下滚一屏 → 调用 maybeFill() → 记录 scrollY」 |
| 实际结果 | 轨迹 `0→752→1503→1892→2644→3396`；每一步用户滚动后与补位后 scrollY **完全相同**；**扩展改动位置次数 = 0** |
| 分页请求 | 1 次（由 Discourse 自身的无限滚动触发，非扩展强制） |
| 判定 | **PASS** |

### C. 过滤后列表变短时的原地补位（**关键用例**）

| 项 | 内容 |
|---|---|
| 测试前状态 | `scrollY=0`，用户从未滚动；临时把 26 个真实 Topic 标成感兴趣以缩短列表 |
| 操作步骤 | 标记后**立刻**在同一次插件世界求值里读门控 → 调用 `maybeFill()` → 等 2.5 秒 → 再调用一次 |
| 实际结果 | 门控 `{sentinelInView: true, visibleHomeRows: 4, shouldLoadMore: true}`；`maybeFill=true`；**分页请求 `/latest.json?no_definitions=true&page=1`**；行数 `30→59`；**`scrollY` 始终为 0**；第二次 `maybeFill=false` 且 **0 请求** |
| 预期结果 | 列表变短 → 哨兵本就在视口内 → 允许补位；用户滚动位置保持 0；不重复触发 |
| 判定 | **PASS** |

**这是最能说明问题的一条**：用户完全没滚动，列表被过滤短了，
扩展**在用户当前位置原地补位**，页面没有任何跳变。

## 6. 请求次数与触发条件

### 触发条件（全部满足）

```
激活池 = HOME
AND 本次路由触发次数 < 2
AND 距上次触发 ≥ 3000ms
AND 可见主信息流行数 < 8
AND .load-more-sentinel 已在视口内（含下方 120px）
```

### 实测请求数

| 场景 | 分页请求 | 说明 |
|---|---|---|
| A 顶部（哨兵在视口外） | **0** | 门控正确拦截 |
| B 五次滚动 | 1 | 来自 Discourse 自身的无限滚动 |
| C 列表变短（哨兵在视口内） | **1** | 扩展派发 scroll 驱动原站加载，词条触发 |
| C 第二次 maybeFill | **0** | 加载后哨兵已被推离视口 → 门控关闭 |
| 本地 A（哨兵在视口外） | 0 | — |
| 本地 C（加载后再次调用） | 0 | 不重复 |

**没有出现重复请求或循环触发。**

### 关于"DOM 更新 → observer → 再触发"的循环风险（你特别提示的点）

已从两个层面封住：

1. **物理层面**：加载新内容会把哨兵**推向下方**，从而离开视口 →
   `sentinelInViewport()` 立即变 false。本地与真实站点的"第二次 maybeFill"实测都返回 false 且 0 请求。
2. **计数层面**：`MAX_LOADS_PER_ROUTE = 2` 是硬上限，与 DOM 变化无关；
   `dispatchPending` + 600ms 冷却避免同一批 DOM 变化触发多次派发。

## 附：本轮暴露的工作流改进

这次是**第一次由真实站点发现的问题反向推动 fixture 升级**：

```
真实站点发现：哨兵在文档底部 → scrollIntoView 会打断阅读
        ↓
回写 fixture：补 .load-more-sentinel + 分页 + 模拟原生无限滚动
        ↓
本地也能复现/验证同类行为（原先本地完全测不到自动补位）
        ↓
修 P1 → 本地 49/49 → 真实站点 4/4
```

值得保留的做法：**凡是真实站点上才有的机制，fixture 必须也具备，否则那部分行为在本地永远是盲区。**
