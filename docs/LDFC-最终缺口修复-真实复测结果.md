## 1. 本轮修复的发现层缺口

### 【问题】真实站点实测

上一个复测目标 `2902024` 暴露的：

```
它当时: /latest.json 第一页带 unread_posts = 3
        不在 tracking 快照里
        不在 /unread.json 第 0 页
↓
本地记录 lastRead=59 / unread=3（元数据同步拿到的）
但 inNewReply = false（发现层看不到它）
↓
一个确实有新回复、且已被标成感兴趣的 Topic，永远不进入「新回复」
```

根因：P0-1 那次修复把 `/latest.json` 的未读字段**整个**从新回复判定里删掉了
（因为它在真实站点 28/30 为 null）。但**为 null 的恰恰是用户没互动过的帖子**；
要检测的「感兴趣 / 已读」正是用户互动过的那批 —— 对它们该字段是可靠的。

### 【修复】四个来源职责分离，不合并成"统一真相"

| 来源 | 职责 | 约束 |
|---|---|---|
| `/latest.json` 的 `unread_posts` | **发现信号**（非 null 数值 > 0） | `null` **绝不**当 0 |
| `topicTrackingStates` | 零请求发现 / 预筛 | `last_read_post_number` 为 null 时**不用**（否则把"从未读过"推成"整帖未读"） |
| `/unread.json` 第 0 页 | 自然时机发现补充 | — |
| `/t/<id>.json` | **完成确认**（唯一清除依据） | — |

**关键约束**：发现层**只标记、绝不清除**。任何来源的 `unread = 0` 都不是"已处理完"的证据。

**未新增任何请求** —— 三个发现来源的数据本来就已经在手上。

## 6. 我在本次复测中犯的一个错误（如实记录）

**首轮断言写得太死，导致结果误报为 FAIL。**

我断言"服务端会恰好停在第 182 楼"：

```js
判定: afterSync.state?.lastReadPostNumber === N + 1   // 期望 182
```

实际服务端推进到了 **185**（渲染了 176–197，Discourse 按自己的阅读判定推进）。
于是断言失败，输出 `FAIL`。

**但原始数据本身证明功能是对的**：

```
lastRead: 181 → 185
第一条未读: /182 → /186        ← 186 = 185 + 1 ✓
```

**真正的不变式不是"停在 N+1"，而是「第一条未读 = 当前 lastRead + 1」。**
我已把断言改成这个不变式（以及步骤 2 改为"服务端推进到 > N 且仍未读完"）。

**结论：这次 FAIL 是测试断言的问题，不是产品缺陷。** 功能实际按预期工作。
（无法重跑验证，因为该帖已被读完 —— 这一点也如实记录。）

## 9. 其他观察（未修，仅记录）

**tracking 的语义比 `/unread.json` 宽**（实测）：

```

/unread.json 报告:          30
```

原因是 `unreadFrom()` 把 `last_read_post_number = null` 当成"整帖未读"。

**本轮已做了防护**：发现层现在要求 tracking 那一路的 `lastReadPostNumber !== null`，
并新增了回归断言（fixture 106）防止将来再被放大。
`trackingState.unreadFrom()` 本身**未改** —— 它仍可用于其它展示场景。
